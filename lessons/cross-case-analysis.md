## 1. 事例の類型

21事例は、大きく6つの型に分けられる。

| 類型 | 事例 | 特徴 |
|---|---|---|
| **A. ランサムウェアで事業が止まる** | 名古屋港、サンリオ、KADOKAWA、白梅豊岡病院、アサヒ、アスクル、ニチレイ、REXT Holdings | 基幹・物流・院内システムが暗号化され、受注・出荷・診療・物流・店舗運営が止まる。売上と決算への影響が大きい |
| **B. 委託先がランサムウェアに遭い、預かったデータが漏れる** | イセトー、穴吹ハウジングサービス（アスクルの3PL事業も一部該当） | 自社の事業停止は限定的でも、委託元・入居者・取引先の情報が大量に漏れ、多数の組織に波及する |
| **C. システムを壊さずに情報を抜く** | アフラック、KDDI、IIJ、損保ジャパン、PR TIMES、さくらインターネット、パーク24、ブックオフ、日本交通 | 暗号化はされず、Webアプリの機能の悪用や脆弱性の悪用、長期潜伏によって大量の個人情報・認証情報が引き出される |
| **D. 補助的なクラウド・周辺システムが侵入口になる** | ホソカワミクロン、損保ジャパン | 基幹システムではなく、業務の周辺で使うクラウドサービスや独立したサブシステムが侵入口になる。件数は小さくても機微情報が漏れる場合と、逆に周辺システムに大量データが集積していた場合の両方がある |
| **E. 管理の「積み残し」が突破口になる** | PR TIMES（コロナ禍の暫定設定）、サンリオ・白梅豊岡病院（リモートアクセス機器） | 過去の緊急対応や運用上の一時的な設定が、棚卸しされないまま何年も残り、侵入口になる |

## 3. 共通パターン

### パターン1: 入口は「境界機器」「例外」「保守経路」「周辺のクラウド」

- **VPN・ネットワーク機器**：名古屋港（保守用VPN）、イセトー（VPN）、アサヒ（拠点のネットワーク機器）、穴吹ハウジングサービス（グループの通信機器）、REXT Holdings/D&M（VPN機器）、サンリオ（リモートアクセス機器）、白梅豊岡病院（VPN）。
- **例外・委託先**：アスクル（委託先の管理者アカウントだけMFAの例外）、名古屋港（保守ベンダー用の入口に IP 制限なし）。
- **補助的なクラウド**：ホソカワミクロン（業務の中心ではない、補助的なクラウドストレージの1アカウント）。
- **管理漏れの設定**：PR TIMES（コロナ禍に追加し、追加経緯が不明になっていたIPアドレスと、不使用の共有アカウント）。
- どれも「全体としては対策していたが、**管理が行き届いていない一点**」から侵入されている。アサヒ、イセトー、穴吹ハウジングサービスは、再発防止策として **VPNそのものを廃止** した。**21事例中7事例がVPN・リモートアクセス機器を侵入口**としており、業種（港湾、印刷、飲料、不動産、テーマパーク、医療、小売）を問わない最頻出パターンであることが裏付けられている。

### パターン2: パッチと認証という「基本」の欠如

- イセトー：VPNを約3年アップデートせず、管理者パスワードは7年間同じ、MFAなし。
- 名古屋港：VPNと物理サーバーの脆弱性を数か月放置。
- アサヒ：パスワードの脆弱性から管理者権限を奪われた。
- ホソカワミクロン：漏えい・推測された認証情報でクラウドストレージにログオンされた。
- PR TIMES：3層の認証（IP制限・BASIC認証・パスワード）があっても、「なぜ許可されているか分からないIPアドレス」という1つの管理漏れで突破された。
- 高度な攻撃ではなく、**基本の未実施・管理の緩み** が原因の大半を占める。

### パターン3: 管理者権限を奪われると、防御もバックアップも無力化される

- アスクルでは、EDRを無効化され、バックアップも削除された。
- 管理者権限を奪われると、暗号化、バックアップ削除、ログ消去まですべてできてしまう。特権IDの管理が防御の要になる。

### パターン4: 気づくまでに時間がかかる

- 損保ジャパン約5日、アサヒ約10日、PR TIMES約2週間、アフラック約2週間、KDDI約1か月、アスクル約4か月（報道）、**IIJ約8か月**、**さくらインターネット約3年**。
- アスクルは侵害されたサーバーに EDR がなく、24時間監視もしていなかった。アフラックは、通常の利用と見分けがつかなかった。さくらインターネットは、契約管理システムへの不正アクセスが2023年4月から2026年3月まで気づかれなかった。
- **監視の空白地帯** と、**「量」や「時間帯」の異常を見る仕組み** がないと、準備期間を活かせない。さくらインターネットの事例は、**ログの保管期間が短いと、数年単位の侵害そのものに気づけない**ことを示している。一方、損保ジャパンのように**5日で検知できた事例もあり**、検知の速さと組織規模・業種の間に単純な相関はない。

### パターン5: ログとバックアップが残らない

- ログ：名古屋港とイセトーは VPN のログを取っておらず、アスクルは委託先 PC のログが消え、原因を断定できなかった。
- バックアップ：名古屋港は3日分しかなく、中身もマルウェアに汚染されていた。アスクルは同じ場所のバックアップが削除・暗号化された。
- IDCフロンティア：4ゾーンの顧客データは「取り出しや復元が困難な見通し」で、復元は顧客自身が保持するバックアップからのみ可能と案内された（第3報）。別の事業者の環境に保管していた事業者は早期に移行できた（報道ベース）。バックアップは「別の場所」だけでなく「別の事業者」に置くことが、復旧の差になった。
- ログが残っていないと、**原因が分からず、漏えい範囲も「おそれ」として広く取らざるを得ない**（アスクル、アサヒで件数が拡大）。

### パターン6: 共有基盤・共通システムは被害を増幅する

- KADOKAWA：同じデータセンターを共有していたため、ニコニコへの攻撃が出版・経理に波及した。
- KDDI：1つのメール基盤の脆弱性が、6社のISP・1,200万人に及んだ。
- 名古屋港：港全体の共通システムが止まり、港湾物流全体が止まった。
- イセトー：1社の委託先から、約100団体に波及した。
- 穴吹ハウジングサービス：グループの通信機器から侵入され、自治体（松山市営住宅）を含む委託元にまで波及した。
- IDCフロンティア：クラウド基盤そのものがランサムウェアに遭い、直接の契約者495の企業・自治体に加え、その上で動くサービスにも影響が連鎖した（自治体サイトや物流拠点の入出荷の停止も報じられている）。さらに、基盤上のメール配信サービスを使っていたJR東日本・ビューカードは、最大約609万件の情報が閲覧・取得された恐れを公表した。停止だけでなく**漏えいも連鎖する**。
- REXT Holdings：同じグループ内で、D&M（6月）とREXT社（8月）の2か月足らずのうちに別々のランサムウェア被害が発生し、**グループ内でのセキュリティ水準のばらつき**が疑われる。

### パターン7: 「ルールはあった」が守られていなかった

- イセトー：委託元のデータは業務系ネットワークだけで扱うルールがあったが、明文化されておらず、3部署が約5年間違反していた。ルールが守られていれば漏えいはなかった。
- KDDI：パスワードの平文保存は一部のプロバイダ側の事情。提供側と利用側の責任分界があいまいだった。

### パターン8: 手作業の代替手段が被害を抑える

- 名古屋港：システムなしで荷役を続けた。KADOKAWA：アナログ対応で新刊の供給を維持した。アサヒ：手作業で受注・出荷した。穴吹ハウジングサービス：営業活動自体は発生当初から継続した。
- 一方で、アスクル（自動倉庫）やニチレイ（冷蔵倉庫）、REXT Holdings（店舗のキャッシュレス決済・EC発送）のように、**IT と OT が結びついた現場、または決済・物流のような即時性が求められる機能ほど手作業での代替が難しい**。

### パターン9: 影響は1年近く続く

- 決算発表の延期（アサヒ、アスクル）、数十〜数百億円の減益（アサヒ、アスクル、KADOKAWA、ニチレイ）、役員報酬の減額・返納（アスクル、アフラック）、行政指導（アスクル、イセトー、KDDI）。
- 個人情報の通知、問い合わせ対応、行政への定期報告（KDDI は少なくとも1年間、四半期ごと）が長く続く。

### パターン10: 「おそれ」の見積もりは、増えることも減ることもある

- アサヒ・アスクルは件数が後から**拡大**した。一方、穴吹ハウジングサービスは、当初「最大約49.6万件」としていた漏えいのおそれが、最終的な精査で**207,773件に縮小**した。
- 最初の「おそれ」の発表は、安全側に広く見積もった暫定値であることが多く、確定までは変動しうる前提で読む必要がある。

### パターン11: 楽観的な暫定評価は覆ることがある

- REXT Holdingsは、第2報（8/14）で「外部漏えいの可能性は極めて低いと推定」としたが、第4報（9/11）で流出情報の公開を確認し、説明が覆った。
- 調査途中の暫定的な安心情報は、後から訂正されるリスクを伴う。「まだ分からない」と明確に伝える方が、結果的に信頼を損ねにくい可能性がある。

### パターン12: 機微性の高いデータ（画像・番号）は影響が長引く

- パーク24：運転免許証などの本人確認書類の**画像**が約160万件流出。なりすましに直結しうる情報で、氏名・住所だけの漏えいより深刻度が高い。
- ホソカワミクロン：件数は約1,728件と小さいが、**マイナンバー**を含む。
- 白梅豊岡病院：氏名・住所に加えて**病名**という医療特有の要配慮個人情報が漏えいした。
- 件数の大小だけでなく、**情報の種類（画像、マイナンバー、病名、口座情報など）による深刻度の違い**を、再発防止の優先順位づけに反映すべき。

### パターン13: 「漏えいのおそれ」がゼロに確定することもある

- サンリオは、2月に「最大約200万件」の漏えいのおそれを公表したが、8月の最終調査で**漏えいは確認されなかった**。穴吹ハウジングサービス（おそれが縮小）よりさらに踏み込んで、最終的に「ゼロ」に至った事例。
- 初期の「おそれ」の公表は安全側に広く見積もる一方、**確定までに半年程度かかる**ことも珍しくない。利用者・投資家は、この間の不確実性を前提に情報を受け取る必要がある。

### パターン14: 緊急対応の「その場しのぎ」が長期間残る

- PR TIMES：コロナ禍のリモートワーク移行時に追加したIPアドレスが、追加の経緯が分からないまま5年近く残っていた。
- 緊急時に暫定的に開けた「穴」は、平時に戻すタイミングを逃すと、そのまま最大の弱点として残り続ける。**緊急対応には必ず「見直し期限」を設定する**運用が必要。

### パターン15: 攻撃者の主張と企業の公式発表がズレることがある

- 日本交通：攻撃者（AiLock）は「2.9TBのデータを窃取した」とダークウェブ上で主張しているが、企業側は「マルウェア感染」「流出の可能性」とのみ説明し、ランサムウェアという言葉も使っていない。
- ダークウェブ上の攻撃者の主張は、被害を誇張する動機（身代金交渉や評判の誇示）を持ちうる一方的な情報であり、企業の公式発表と食い違う場合は、どちらもそのまま鵜呑みにせず「未確認」として扱う必要がある。

## 4. 再発防止策に共通して登場する項目

21事例が公表した再発防止策を項目ごとに集計すると、次のようになる（カッコ内は該当事例。複数の項目に該当する事例もある）。

- **VPN廃止・リモートアクセスの制限**（8件）：名古屋港、イセトー（VPN廃止）、穴吹ハウジングサービス（VPN廃止）、アサヒ（VPN廃止）、アスクル、サンリオ、白梅豊岡病院、REXT Holdings/D&M
- **MFA・認証と権限管理の強化**（8件）：イセトー、KADOKAWA（アカウントリセット）、穴吹ハウジングサービス、アサヒ、アスクル、アフラック（認証・認可）、さくらインターネット（権限総点検）、PR TIMES（二段階認証・IP制限）
- **EDR・監視（SOC）の強化**（8件）：名古屋港、穴吹ハウジングサービス（24/365）、アサヒ、アスクル、アフラック（大量アクセス監視）、KDDI（EDR導入）、ニチレイ、さくらインターネット（EDR拡大）
- **ネットワーク分離**（5件）：イセトー（データを移せない環境）、KADOKAWA（環境の再構築）、穴吹ハウジングサービス（SASE導入）、アサヒ、アスクル、さくらインターネット（多層アクセス制御）
- **パッチ・脆弱性管理**（3件）：名古屋港、イセトー、KDDI
- **バックアップ・ログの強化**（4件）：名古屋港、穴吹ハウジングサービス、アサヒ、アスクル、さくらインターネット（ログ保管見直し）
- **BCP・対応手順・訓練**（6件）：名古屋港、アサヒ、アスクル、KDDI（初動体制）、ニチレイ、さくらインターネット（訓練強化）
- **データの保管ルール・削除・監査**（2件）：イセトー、アサヒ（規程改定・監査）
- **設計レビュー・侵入テスト・外部評価**（7件）：名古屋港、KADOKAWA（外部チェック）、ホソカワミクロン（助言）、アサヒ、アスクル、アフラック、KDDI（コード分析）、さくらインターネット（定期監査）
- **責任者・組織・ガバナンス**（8件）：名古屋港（CISO指定）、KADOKAWA（監査委員会）、穴吹ハウジングサービス（教育・CSIRT）、アサヒ（独立組織・専任役員）、アスクル、アフラック（体制強化・報酬返納）、KDDI（報告体制）、さくらインターネット（経営層報告）、REXT Holdings（体制再構築、方針のみ）

日本交通、パーク24、ブックオフ、IDCフロンティア、損保ジャパン、白梅豊岡病院、IIJの一部は、2026-10-10時点で具体的な再発防止策を公表していない（調査継続中、または行政への報告後に開示予定のため）。IIJは振る舞い検知の強化とWAFの多層化を実施済み。PR TIMESは段階的な実装スケジュール（2026年3月まで）を公表している点が特徴的。

※ 空欄・未言及は「その対策を公表していない」という意味で、「実施していない」とは限らない。REXT Holdings、パーク24、ブックオフ、IDCフロンティア、日本交通、白梅豊岡病院、損保ジャパンは、2026-10-10時点で調査継続中のため、具体策の多くが未公表。

## 5. 自社点検チェックリスト

21事例の原因と再発防止策から逆算した点検項目です。（ ）内は、その項目の根拠になった事例です。

### 入口（初期侵入）
- [ ] VPN・ルーター・ファイアウォールなどインターネットに面した機器を、**拠点・グループ会社・保守ベンダー用の分まで** 台帳で把握しているか（アサヒ、名古屋港、穴吹ハウジングサービス、サンリオ、白梅豊岡病院）
- [ ] それらの機器の脆弱性情報を追い、期限内にパッチを当てているか（イセトー、名古屋港）
- [ ] 保守用のリモート接続に、IP アドレス制限・MFA・使うときだけ有効にする運用を適用しているか（名古屋港）
- [ ] すべてのリモートアクセス（**委託先・保守ベンダー用を含む**）に MFA を適用しているか（アスクル、イセトー）
- [ ] MFA の **例外** を一覧化し、期限と代わりの対策を決めているか（アスクル）
- [ ] フィッシングに強い認証（FIDO2 など）や、窃取されたアカウントの不審なログインの検知があるか（KADOKAWA）
- [ ] 組み込んでいる第三者製ソフトウェアを把握し（SBOM）、脆弱性情報を追えるか（KDDI、IIJ）
- [ ] **IT部門が正式に把握していない、業務の周辺で使っているクラウドサービス**（部門契約のストレージ等）を棚卸しし、同じ水準のセキュリティを適用しているか（ホソカワミクロン）
- [ ] 業務時間外の異常なログイン試行・横展開の兆候を検知できるか（アサヒ、穴吹ハウジングサービス）
- [ ] **過去の緊急対応（災害・パンデミック対応等）で追加した例外設定**を定期的に棚卸しし、追加理由が分からない設定を削除しているか（PR TIMES：コロナ禍のIPアドレス追加が5年近く放置）
- [ ] 独立したサブシステム・周辺システムに、想定以上の量の顧客データが集積していないか（損保ジャパン：指標管理用システムから最大1,748万件）

### 認証・権限
- [ ] 管理者パスワードは十分に強く、長期間同じままになっていないか（イセトー、アサヒ）
- [ ] 特権アカウントを常時付与せず、使うときだけ付与する運用になっているか（アサヒ、アスクル）
- [ ] 利用者のパスワードを平文・復元可能な形で保存していないか（KDDI）
- [ ] クラウドサービスのアカウントにも、社内システムと同水準の多要素認証・アクセス制限を適用しているか（ホソカワミクロン）
- [ ] **共有アカウント**を洗い出し、不要なものを削除しているか。個人アカウントへの統一を進めているか（PR TIMES：不使用の共有アカウントが悪用された）
- [ ] 複数層の認証（IP制限・BASIC認証・パスワード等）がある場合、**各層が本当に正しく設定されているか**を定期的に検証しているか（PR TIMES：3層あっても1層の管理漏れで突破された）

### Webアプリケーション（類型C）
- [ ] データを照会するたびに「その利用者がそのデータを見てよいか」（認可）を確認しているか（アフラック）
- [ ] 利用者・代理店ごとの照会件数の上限やレート制限、大量照会のアラートがあるか（アフラック）
- [ ] 設計レビュー・侵入テストで、ビジネスロジックの悪用まで想定しているか（アフラック）

### 検知
- [ ] サーバー（データセンター、物流システムを含む）に EDR が入っているか。対象の抜けはないか（アスクル、KDDI）
- [ ] EDR が停止・無効化されたことを検知できるか（アスクル）
- [ ] 24時間365日、アラートを見て対応できる体制があるか（アスクル）
- [ ] 業務時間外の管理者ログインや、普段と違うアクセス量・アクセス先を警告できるか（アサヒ、アフラック）

### ログ
- [ ] VPN 機器を含む入口のログを取得し、攻撃者が消せない場所に保存しているか（名古屋港、イセトー）
- [ ] ログ取得の設定を定期的に確認しているか（イセトー）
- [ ] 委託先の端末についても、ログの保全や調査協力を契約で定めているか（アスクル）
- [ ] ログの**保管期間**は、数年単位の潜伏を発見できる長さになっているか（さくらインターネット：約3年間気づかれなかった事案あり）

### バックアップと復旧
- [ ] バックアップを本番とは別の認証基盤・別の場所で管理し、オフラインまたは書き換え不可の複製があるか（アスクル）
- [ ] 十分な世代を持ち、復元後にマルウェアスキャンをする手順があるか（名古屋港）
- [ ] 開発・評価環境もバックアップの対象にしているか（名古屋港）
- [ ] 実際にバックアップから戻す訓練をしているか（アサヒ、アスクル）
- [ ] クラウドを使っている場合、バックアップを同じクラウド基盤の中だけに置いていないか。基盤の事業者ごと止まっても戻せる、別の場所・別の事業者の複製があるか（IDCフロンティア。復元は顧客自身のバックアップからのみ）

### データ管理
- [ ] 委託元・顧客のデータを保管してよい場所を明文化し、技術的にそれ以外へ移せないようにしているか（イセトー）
- [ ] 業務が終わったデータを期限どおりに削除しているか（イセトー）
- [ ] ルールが守られているかを定期的に監査しているか（イセトー）

### 事業継続
- [ ] システムが止まったときに、受注・出荷・請求・経理を手作業で回す手順があるか（名古屋港、KADOKAWA、アサヒ）
- [ ] 事業ごとに基盤・ネットワーク・管理者権限を分け、被害を局所化できるか（KADOKAWA）
- [ ] 災害だけでなく **サイバー攻撃を想定した BCP** があるか（名古屋港）
- [ ] IT と OT（倉庫・工場の設備）を横断して、停止の影響を評価しているか（アスクル、ニチレイ）
- [ ] 再開前に、どこまで安全性を確認するかの基準を決めているか（名古屋港）

### 委託先・サプライチェーン
- [ ] 委託先のパッチ・認証・データの保管場所・削除まで確認しているか。契約に書いているか（イセトー）
- [ ] 自社のサービスが依存しているクラウド・ホスティング基盤を、メール配信などの外部サービスの先（再委託先）まで含めて把握し、基盤が止まったときの代替手順（別環境への切り替え、顧客への案内）を決めているか（IDCフロンティア、JR東日本）
- [ ] 共通基盤を提供する側・使う側の、セキュリティ設定の責任分界が明確か（KDDI）
- [ ] グループ会社ごとにセキュリティ水準がばらついていないか、グループ横断で基準を統一しているか（REXT Holdings：2か月足らずで2子会社が別々の被害）

### データの種類ごとのリスク評価
- [ ] 運転免許証などの**本人確認書類の画像**を保有している場合、保存期間・暗号化・アクセス制御を特に厳しくしているか（パーク24）
- [ ] マイナンバーなど機微性の高い情報を扱うシステム（規模が小さくても）は、最高水準の保護を適用しているか（ホソカワミクロン）
- [ ] 病名・診療情報など**要配慮個人情報**を扱う場合、一般的な個人情報より厳格な管理をしているか（白梅豊岡病院）
- [ ] 未公表の決算情報・新商品情報など、**インサイダー取引に悪用されうる情報**を扱っている場合、専用の保護策があるか（PR TIMES）

### 初動・開示
- [ ] インシデント時にすぐ相談できるセキュリティ専門家（保守ベンダーとは別）がいるか（名古屋港）
- [ ] 第1報で何を伝えるか、確定前でも早めに公表する判断基準があるか（KDDI）
- [ ] 「漏えいを確認」と「漏えいのおそれ」を分けて説明し、件数が増える前提で通知できるか（アサヒ、アスクル）。逆に、初期の見積もりが過大で、後に縮小することもある（穴吹ハウジングサービス）
- [ ] 調査途中の「可能性は低い」といった暫定評価を、断定的に公表していないか（REXT Holdings：後に覆った）
- [ ] 漏えい情報の拡散に対する削除要請・法的措置の手順があるか（KADOKAWA）
- [ ] 個人情報保護委員会・所管官庁（金融庁、総務省、厚生労働省など）・警察への報告手順を把握しているか（全事例）
- [ ] 身代金を支払わない・交渉しないといった方針を、平時に経営として決めているか（アスクル）
- [ ] ダークウェブ上の攻撃者の主張を、そのまま事実として扱わず「未確認情報」として慎重に対応する方針があるか（日本交通）
- [ ] 医療機関の場合、厚生労働省の初動対応支援チームなど公的な支援の枠組みを把握しているか（白梅豊岡病院）

### ガバナンス
- [ ] セキュリティの責任者（CISO・専任役員）と、独立した所管組織があるか（アサヒ、名古屋港）
- [ ] 取締役会・監査委員会がサイバーリスクを監督しているか（アサヒ、KADOKAWA）
- [ ] 経営層がパッチ・パスワード・ルール遵守の状況を把握できているか（イセトー）
- [ ] グループ会社・海外拠点を含めた共通のセキュリティ基準があるか（アサヒ、REXT Holdings）
- [ ] 金融機関・通信事業者など業法上の規制がある業種は、個人情報保護法に加えて業法上の報告義務（報告徴求命令、通信の秘密の指導等）への対応体制があるか（損保ジャパン、KDDI、IIJ）
